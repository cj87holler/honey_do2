<task type="auto">
  <name>Task 2: Confirm the workflow actually runs and passes</name>
  <files></files>
  <action>


If it fails, read the logs and fix forward on `dev` — a red first run is information, not a

  </action>

  <done>At least one completed CI run exists and its check name is known</done>

<task type="checkpoint">
  <name>Task 3: Make the check required, enforced for admins</name>
  <files></files>
  <action>
Confirm with the user before changing protection rules.

Current state per STATE.md: PR required, 0 approvals, `enforce_admins` false,
`required_status_checks` null.

Apply the locked decision — required status checks plus `enforce_admins: true`:

```bash
gh api -X PUT repos/cj87holler/honey_do2/branches/main/protection \
  -H "Accept: application/vnd.github+json" \
  --input - <<'JSON'
{
  "required_status_checks": { "strict": true, "contexts": ["<exact check name from task 2>"] },
  "enforce_admins": true,
  "required_pull_request_reviews": { "required_approving_review_count": 0 },
  "restrictions": null
}
JSON
```

The protection API replaces the whole object rather than patching it, so every field must be sent
together — omitting `required_pull_request_reviews` would silently drop the existing
PR-required rule. Read back the result with
`gh api repos/cj87holler/honey_do2/branches/main/protection` and diff it against what STATE.md
recorded, rather than trusting the write succeeded.

`enforce_admins: true` means the user cannot merge a red PR on their own repo. That is the point
of criterion 4, and it is reversible by flipping the same field back.
  </action>
  <verify>gh api .../branches/main/protection shows the CI check under required_status_checks.contexts and enforce_admins.enabled true</verify>
  <done>Protection reflects both the required check and admin enforcement</done>
</task>

<task type="auto">
  <name>Task 4: Demonstrate that a failing check actually blocks the merge</name>
  <files></files>
  <action>
Criterion 4 says a PR with a failing check *is blocked from merging*. Verify that as an observed
behavior, not an inferred one.

Push a deliberately failing commit to a scratch branch, open a PR from it, let CI go red, and
confirm GitHub reports the PR as not mergeable:

```bash
gh pr view <n> --json mergeable,mergeStateStatus
```

Expect `mergeStateStatus: BLOCKED`. Then close the PR and delete the scratch branch. Do this on a
throwaway branch, never on `dev`, so the proving PR from task 1 stays clean.

If GitHub reports the PR as mergeable despite a red check, protection is misconfigured — go back
to task 3 rather than declaring the criterion met.
  </action>
  <verify>gh pr view reports mergeStateStatus BLOCKED on the failing PR; scratch branch and PR cleaned up afterwards</verify>
  <done>Blocking behavior observed directly, then the test artifacts removed</done>
</task>
