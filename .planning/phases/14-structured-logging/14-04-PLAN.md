  <action>
Create `tests/logger/instrumentation.test.ts` with the `// @vitest-environment node` pragma on line 1
and explicit `vitest` imports. No mocks; this is a source-text gate. Read each file with
`fs.readFileSync(path.join(process.cwd(), relPath), "utf-8")` and strip comments before every
assertion — drop `/* ... */` blocks, then drop lines whose trimmed form starts with `//` — so a
future explanatory comment can neither satisfy nor break a gate. Factor the stripper into a local
helper used by every case.

Define `const INSTRUMENTED = ["src/lib/actions/task.ts", "src/lib/actions/invite.ts", "src/lib/actions/admin.ts", "src/lib/actions/hive.ts", "src/app/api/auth/[...all]/route.ts"]`
and drive the assertions with `it.each` / a `for` loop so a per-file failure names the file.

Assertions:

  1. **Import gate.** For every entry in `INSTRUMENTED`, the stripped source matches
     `/^import\s*\{[^}]*\blogger\b[^}]*\}\s*from\s*["']@\/lib\/logger["']/m`. Assert on this regex,
     not `toContain("@/lib/logger")`, so a stray mention in a string cannot satisfy the gate.
  2. **Call-site gate.** For every entry, the stripped source matches
     `/\blogger(?:\.(?:info|warn|error|debug)|\[\s*["'`](?:info|warn|error|debug)["'`]\s*\]|\[\s*[A-Za-z_$][\w$]*\s*\])\s*\(/`
     at least once — an unused import does not count as "used by". The alternation is deliberate:
     14-03's status-to-level mapping (`>= 500` error, `>= 400` warn, else info) is equally
     idiomatic as an `if/else` chain of literal calls or as computed dispatch
     (`logger[level]({...})`). A literal-only regex would fail a correct computed-dispatch
     implementation that passes 14-03's own tests, producing an avoidable failed-verify loop in
     this wave. Accept both forms rather than constraining 14-03's implementation style.
  3. **Coverage count.** `INSTRUMENTED.length === 5`, and each of the four roadmap areas is
     represented: the list contains a path matching `/actions\/task\.ts$/` (task-mutation),
     `/actions\/invite\.ts$/` (invite), `/actions\/admin\.ts$/` (admin), and
     `/api\/auth\/.*route\.ts$/` (auth).
  4. **Forbidden-field scan.** For every entry, extract each logger call's first argument
     text (match from `logger` up to the matching close of the object literal; a non-greedy
     `/logger(?:\.(?:info|warn|error|debug)|\[[^\]]*\])\s*\(\s*\{([^}]*)\}/g` over the stripped
     source is sufficient because the field policy only permits flat objects) and assert the
     captured text does NOT match
     `/\b(token|password|tempPassword|hashed|email|text|cookie|name)\b/`. The permitted vocabulary —
     `hiveId`, `taskId`, `inviteId`, `userId`, `memberId`, `role`, `status`, `reason`, `from`, `to`,
     `honeyValue`, `expiresAt`, `method`, `authRoute`, `durationMs`, `err` — contains none of those
     words, so a match means a real policy violation. On failure the assertion message must include
     the offending file path and the captured argument text. The bracket alternation matters more
     here than in assertion 2: a literal-only pattern fails *loudly* in the call-site gate, but in
     this scan it would fail *silently* — a computed-dispatch call carrying `email` or `token` would
     simply never be extracted, and the file would pass the security gate without ever being
     scanned. Both forms must be matched.
  5. **Sanity anchor.** Each stripped source is non-empty and longer than 200 characters, so a
     deleted or emptied file fails loudly rather than passing every `not.toMatch`.
  6. **Negative control.** `src/middleware.ts`, read and stripped the same way, matches neither the
     import regex from assertion 1 nor the call-site regex from assertion 2. This duplicates plan
     14-01's criterion-4 gate on purpose: 14-01 asserts absence of the string, this asserts absence
     of a working import, and the two fail for different mistakes.
  </action>
