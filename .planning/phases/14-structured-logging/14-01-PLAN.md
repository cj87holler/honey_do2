<resolved_decisions>
Phase 14 research left three decisions open. All three are resolved here. Do not re-open them.

**D-14-A — `src/lib/logger.ts` exports a factory, not only a singleton. RESOLVED: factory.**
The module exports `buildLoggerOptions()` (pure options builder), `makeErrSerializer()` (pure
serializer factory), `createLogger(options?, destination?)` (constructor), and `logger` (the
singleton, built by calling `createLogger()` with no arguments).
Rationale: the alternative — exporting only a config object and constructing a throwaway `pino()`
inside tests — never exercises the real construction path, so a bug where the singleton forgets to
pass `serializers` would pass every test. Routing the singleton through the same `createLogger` the
tests call means the tests verify the shipped wiring. Cost is three extra named exports.

**D-14-B — how to log "auth". RESOLVED: wrap the Route Handler exports. Do NOT wire Better Auth's
`logger.log` hook.**
The seam is `src/app/api/auth/[...all]/route.ts`, implemented in plan 14-03, not here.
Rationale: success criterion 1 requires the shared logger to be *used by* the auth route. A wrapper
around `toNextJsHandler(auth)`'s `GET`/`POST` exports is code this repo owns, so it is deterministic
and unit-testable. Better Auth's `logger.log` hook has a documented upstream coverage gap
(better-auth#3250, "Logger not, well, logging"; PR #10121 routed only account-linking logs through
it), so it cannot be relied on to emit a single line for sign-in/sign-up/sign-out — an unverifiable
mechanism cannot satisfy a success criterion. `src/lib/auth.ts` is NOT modified in this phase.
Revisit the hook as an additive enhancement once better-auth#3250 closes.

**D-14-C — the custom `err` serializer. RESOLVED: required, implemented here as `makeErrSerializer`.**
pino's `redact.paths` matches object *paths*, never substrings, so a Postgres/`postgres`-driver
connection failure whose `.message` echoes the connection string walks straight past redaction.
Success criterion 2 is unsatisfiable without this. Implemented in Task 1, tested in Task 2.

**Bonus resolution — the transport branch is opt-IN on `development`, not opt-OUT of `production`.**
Research sketched `NODE_ENV !== "production"` for the pino-pretty transport. That is wrong for this
repo: vitest sets `NODE_ENV=test`, so every existing test file that transitively imports an
instrumented server action would spawn a `thread-stream` worker for pino-pretty. The condition is
`resolvedNodeEnv === "development"`. This is also a strictly more literal reading of criterion 3
("pino-pretty is used only in development").
</resolved_decisions>

<logging_field_policy>
This policy is defined once here and is binding on plans 14-02 and 14-03.

ALLOWED log fields (opaque identifiers and enums only):
`hiveId`, `taskId`, `inviteId`, `userId`, `memberId`, `role`, `status`, `reason`, `from`, `to`,
`honeyValue`, `expiresAt`, `method`, `authRoute`, `durationMs`, `err`.

FORBIDDEN log fields (never pass these to any logger call, at any level):
task `text`, hive `name`, user `email`, invite `token`, `tempPassword`, any password or password
hash, raw `session` objects, raw `headers`, raw request bodies, `process.env`.

Message strings are static string literals. Never interpolate user-controlled input into the pino
message argument — put data in the structured object argument, where pino JSON-escapes it.
</logging_field_policy>

2. `export function makeErrSerializer(databaseUrl?: string)` — returns a serializer function
   `(err: unknown) => Record<string, unknown>`. Behavior:
   - Build a `secrets: string[]` array at factory time (not per-call): push `databaseUrl` if it is a
     non-empty string; then, inside a `try`/`catch` that swallows parse failures, push
     `new URL(databaseUrl).password` if that password is non-empty and at least 4 characters long
     (drivers sometimes echo credentials separately from the full URL). Sort `secrets` by length
     descending so the full URL is replaced before its password substring.
   - Define an internal `scrub(value: string)` that runs `replaceAll(secret, "[REDACTED]")` for each
     entry in `secrets` and returns the result unchanged when `secrets` is empty.
   - If the input is an `Error`: serialize with `pino.stdSerializers.err`, then apply `scrub` to the
     result's `message` and `stack` when each is a string. Return the serialized object.
   - If the input is not an `Error`: return `{ type: typeof input, message: scrub(String(input)) }`.

     `{ type: "SerializerError", message: "[unserializable error]" }`.

     building `{ type: err.constructor.name, message: err.message, stack: err.stack }` yourself and
     scrub the same two fields; record the fallback in the SUMMARY.

     `res.headers["set-cookie"]`, `user.email`, `session.user.email`, `DATABASE_URL`,
     `*.DATABASE_URL`, `env.DATABASE_URL`.

     logging email, this makes an accidental raw-object log non-leaking.)
   - `serializers`: `{ err: makeErrSerializer(databaseUrl), error: makeErrSerializer(databaseUrl) }`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server process → stdout → Vercel Runtime Logs | Everything written by pino leaves the process trust boundary and becomes readable by anyone with Vercel dashboard access or a future log-drain integration |
| `process.env` → logged object | `DATABASE_URL` and other deployment secrets live in the same process as the logger and can reach stdout by direct logging or by embedding in a driver error string |
| user input → log record | Task text, hive names, and emails are attacker-controllable strings that end up in a log viewer |
| npm registry → `node_modules` | `npm install pino pino-pretty` executes third-party install-time code |
