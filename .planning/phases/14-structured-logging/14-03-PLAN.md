<resolved_decision>
**D-14-B (resolved in plan 14-01): wrap the Route Handler exports; do NOT wire Better Auth's
`logger.log` hook.** `src/lib/auth.ts` is NOT modified in this phase.

Rationale, restated so the executor does not "helpfully" also wire the hook: Better Auth's internal
logger has a documented upstream coverage gap (better-auth#3250, "Logger not, well, logging"; PR
#10121 routed only account-linking logs through it), so the hook cannot be relied on to emit any line
for sign-in / sign-up / sign-out. A success criterion cannot rest on an unverifiable mechanism. The
route wrapper is code this repo owns, so it is deterministic and unit-testable. Revisit the hook as
an additive enhancement after better-auth#3250 closes.

14-PATTERNS.md flags that **no route handler in this repo has ever wrapped its exports** — there is
no in-repo analog for this specific technique. The full target shape is specified below rather than
left to pattern-matching.
</resolved_decision>

  <action>
Create `src/lib/auth-log.ts` exporting one pure function,
`export function authRouteLabel(rawUrl: string): string`.

**Why this exists.** Better Auth's catch-all route serves paths that carry secrets directly in the
URL — `/api/auth/reset-password/<token>` puts a password-reset token in a path segment, and
`/api/auth/verify-email?token=<token>` puts one in the query string. Logging `req.url`, or even
`new URL(req.url).pathname`, would write a live account-takeover credential to stdout. This function
reduces a URL to a bounded, allowlisted label that cannot carry a secret.

**Algorithm — implement exactly this:**
  1. Parse with `new URL(rawUrl)` inside a try/catch; on any failure return the literal `"unknown"`.
  2. Take `url.pathname`. If it does not start with `/api/auth/`, return `"unknown"`.
  3. Strip that prefix, split the remainder on `/`, and drop empty segments.
  4. If there are no segments, return `"unknown"`.
  5. First segment: return it only if it matches `/^[a-z][a-z0-9-]{0,31}$/`; otherwise the whole
     result is `"unknown"`.
  6. Second segment: include it **only** if it is a member of the fixed allowlist
     `["email", "social", "username", "callback"]`. Any other second segment — including a token —
     is dropped entirely, not truncated and not hashed.
  7. Ignore every segment at index 2 or beyond, unconditionally.
  8. Never read `url.search`, `url.hash`, `url.username`, `url.password`, or `url.host`.
  9. Return `first` or `first + "/" + second`.

Export the allowlist as a module-scope `const` so the test can assert its membership, but keep the
function the only exported symbol beyond it.

Then create `tests/logger/auth-route.test.ts` with the `// @vitest-environment node` pragma on line 1
and explicit `vitest` imports, containing a `describe("authRouteLabel")` block covering:
  - `/api/auth/sign-in/email` → `"sign-in/email"`
  - `/api/auth/sign-up/email` → `"sign-up/email"`
  - `/api/auth/sign-out` → `"sign-out"`
  - `/api/auth/get-session` → `"get-session"`
  - `/api/auth/reset-password/rSbYm4kPq7ZxT2vNw9LcEa1HdG3JuF8Q` → exactly `"reset-password"`, and the
    result does not contain `"rSbYm4kPq7ZxT2vNw9LcEa1HdG3JuF8Q"`
  - `/api/auth/verify-email?token=SUPERSECRETTOKEN` → exactly `"verify-email"`, and the result does
    not contain `"SUPERSECRETTOKEN"`
  - `/api/auth/reset-password/tok/extra/more` → exactly `"reset-password"` (index 2+ always dropped)
  - `/some/other/path` → `"unknown"`
  - `"not-a-url"` → `"unknown"` (and does not throw)
  - `""` → `"unknown"` (and does not throw)
  - A property-style assertion: for 100 randomly generated 32-character path tokens appended to
    `/api/auth/reset-password/`, the returned label is always `"reset-password"` and never contains
    the generated token

Use absolute URLs (`https://honeydo.example` + path) when constructing test inputs, since `new URL`
requires an absolute URL and `Request.url` is always absolute.

**Route file target shape:**
  - Imports: `auth` from `@/lib/auth`, `toNextJsHandler` from `better-auth/next-js`, `logger` from
    `@/lib/logger`, `authRouteLabel` from `@/lib/auth-log`.
  - `const handlers = toNextJsHandler(auth)` at module scope.
  - A module-scope, non-exported `withLogging(method: "GET" | "POST", handler: (req: Request) => Promise<Response>)`
    returning `async (req: Request): Promise<Response>`. Next.js route files should export only the
    HTTP-method handlers, so `withLogging` must not be exported.
  - Inside the returned function:
    - `const authRoute = authRouteLabel(req.url)` and `const startedAt = Date.now()` before invoking
      the handler.
    - `try`: `const res = await handler(req)`, compute `durationMs = Date.now() - startedAt`, select
      the level from `res.status` — `>= 500` → `logger.error`, `>= 400` → `logger.warn`, otherwise
      `logger.info` — emit `{ method, authRoute, status: res.status, durationMs }` with the static
      message `"auth request"`, and `return res` (return the exact same Response object; do not
      clone, re-wrap, or read its body).
    - `catch (err)`: emit `logger.error({ err, method, authRoute, durationMs: Date.now() - startedAt }, "auth request failed")`
      then `throw err` so Next.js's error handling is unchanged.
  - `export const GET = withLogging("GET", handlers.GET)` and
    `export const POST = withLogging("POST", handlers.POST)`.
  - **Hard prohibitions.** The wrapper must NOT touch `req.headers` (they carry the session cookie
    and any Authorization header), must NOT call `req.text()`, `req.json()`, `req.formData()`,
    `req.arrayBuffer()`, or `req.clone()` (the sign-in/sign-up POST body contains the plaintext
    password, and consuming the stream would break Better Auth by leaving the handler an already-read
    body), and must NOT log `req.url` directly — only the `authRouteLabel` result.
  - Add a short comment block at the top explaining WHY the wrapper exists and why only the label is
    logged, matching the `src/lib/db.ts` comment style (explain the reason, not the mechanics).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated internet → `/api/auth/*` | Fully untrusted input: URLs, headers, and request bodies containing plaintext credentials |
| auth request → stdout | Anything the wrapper logs becomes readable by anyone with Vercel Runtime Logs access |
| wrapper → Better Auth handler | The wrapper sits between the request and Better Auth; consuming the body here breaks authentication |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-15 | Information Disclosure | password-reset token in URL path | mitigate | `authRouteLabel` keeps at most two path segments and admits the second only from the fixed allowlist `["email","social","username","callback"]`, so `/api/auth/reset-password/<token>` reduces to `"reset-password"`. Asserted directly and via a 100-iteration property test in Task 1. |
| T-14-16 | Information Disclosure | verification token in query string | mitigate | `authRouteLabel` never reads `url.search` or `url.hash`; enforced by a `grep` acceptance criterion on `src/lib/auth-log.ts` and by a `verify-email?token=` test case. |
| T-14-17 | Information Disclosure | plaintext password in the sign-in/sign-up POST body | mitigate | The wrapper is forbidden from calling `req.json()`, `req.text()`, `req.formData()`, `req.arrayBuffer()`, or `req.clone()`; enforced by `grep` and by a wrapper test asserting the stringified logger calls contain neither the body password nor the email. |
| T-14-18 | Information Disclosure | session cookie / Authorization header | mitigate | The wrapper never touches `req.headers`; enforced by `grep` and by a wrapper test passing a `better-auth.session_token` cookie and asserting it never appears in any logger call. The logger's `redact` paths are a second layer. |
| T-14-19 | Denial of Service | wrapper consuming the request stream | mitigate | Reading the body would leave Better Auth with `bodyUsed === true` and break all sign-in/sign-up. Task 2 asserts `req.bodyUsed === false` after a POST passes through. |
| T-14-20 | Tampering | wrapper swallowing handler errors | mitigate | The catch block logs then `throw err`, preserving Next.js error handling. Asserted by `rejects.toThrow("boom")`. |
| T-14-21 | Repudiation | auth events attributable to a user | accept | The wrapper logs no `userId` because the request is unauthenticated at the wrapper layer and extracting identity would require reading headers or the body — precisely what T-14-17 and T-14-18 forbid. Route label plus status is the observability ceiling for this seam; per-user auth attribution is Phase 16 (Sentry) territory. |
| T-14-22 | Information Disclosure | Better Auth internal logs bypassing the shared logger | accept | D-14-B declines to wire Better Auth's `logger.log` hook because of upstream coverage gap better-auth#3250. Better Auth's own internal output (default minimum level `warn`) continues to go to `console` unstructured. This is a known, bounded gap, documented for revisit after the upstream issue closes. |
</threat_model>
