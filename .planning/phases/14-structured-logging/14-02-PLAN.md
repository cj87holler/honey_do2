<interfaces>
From `src/lib/logger.ts` (created by plan 14-01 — import via the `@/lib/logger` alias):

- `logger` — the pino singleton. Call as `logger.info(obj, "static message")`,
  `logger.warn(obj, "static message")`, `logger.error({ err, ...obj }, "static message")`.
- `buildLoggerOptions`, `createLogger`, `makeErrSerializer` — factory exports; NOT used by this plan.

The logger already redacts `session.token`, `*.password`, `token`/`*.token`, `tempPassword`,
`cookies`, `headers.cookie`, `user.email`, `DATABASE_URL` and scrubs `DATABASE_URL` out of error
`.message`/`.stack`. Redaction is a safety net, not a licence — the field policy below is still binding.
</interfaces>

<logging_field_policy>
Binding, defined in plan 14-01. Repeated here because this plan is where it is applied.

ALLOWED fields: `hiveId`, `taskId`, `inviteId`, `userId`, `memberId`, `role`, `status`, `reason`,
`from`, `to`, `honeyValue`, `expiresAt`, `err`.

FORBIDDEN fields — never pass these to a logger call: task `text`, hive `name`, user `email`, invite
`token`, `tempPassword`, any password or hash, the raw `session` object, raw `headers`.

Levels: `info` for a completed mutation. `warn` for a rejected request (authorization or validation).
`error` only for an unexpected failure caught from the database layer.

Messages are static string literals. User-controlled data goes in the structured object argument only.

Import placement: add `import { logger } from "@/lib/logger"` into each file's existing flat import
block alongside the other `@/lib/*` imports — no separate import group, no blank line inserted.
</logging_field_policy>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server action → stdout | Every added `logger.*` call moves data out of the process into Vercel Runtime Logs |
| server action → client error message | `admin.ts` deliberately narrows what crosses this boundary; instrumentation must not widen it |
| user input (task text, hive name, invite token) → log record | Attacker-controllable strings reaching a log viewer |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-08 | Information Disclosure | `invite.ts` `generateInvite` / `acceptInvite` | mitigate | The invite `token` is a bearer credential for hive membership. It is never passed to a logger call, not even truncated; only `hiveId`/`userId`/`expiresAt` are logged. Gated by the `grep` acceptance criterion in Task 2. |
| T-14-09 | Information Disclosure | `admin.ts` `resetUserPassword` | mitigate | `tempPassword` and the scrypt hash are never logged. New tests assert `JSON.stringify` of all logger call arguments contains neither the mocked temp password nor the mocked hash. |
| T-14-10 | Information Disclosure | `admin.ts` generic re-throw widening | mitigate | The instrumentation changes `catch {` to `catch (err) {` and adds a `logger.error` line only; the `throw new Error("Password reset failed")` literal is unchanged and asserted with `toBe` in a new test, so any future attempt to attach `cause` or enrich the message fails CI. |
| T-14-11 | Information Disclosure | PII in mutation logs | mitigate | Field policy restricts logs to opaque identifiers (`hiveId`, `taskId`, `userId`, `memberId`) and enums. Task text, hive name, and email are forbidden and gated by a negative `grep` in both tasks' acceptance criteria. |
| T-14-12 | Tampering | log forging via task text / hive name | mitigate | Because user-controlled strings are never logged at all in this plan, and message arguments are static literals, there is no path for an attacker-controlled newline to reach a log line. Plan 14-01 Task 2 test 12 additionally proves pino escapes such strings if one ever is logged. |
| T-14-13 | Denial of Service | logging inside a hot path | accept | These are per-mutation server actions at household scale (a handful of writes per user per day), not a request-per-second hot loop. pino's overhead is negligible at this volume. |
| T-14-14 | Elevation of Privilege | swallowed `redirect()` in `createHive` | mitigate | `redirect()` throws `NEXT_REDIRECT` for control flow; a try/catch around it would swallow the redirect and leave an authenticated user on a stale page. Task 1 explicitly forbids wrapping `redirect()` and places the log call before it. |
</threat_model>
