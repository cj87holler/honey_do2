<threat_model>
## Security Threats

### T-01: Secrets in committed files
- **Threat:** Production DATABASE_URL or BETTER_AUTH_SECRET committed to .env or source files
- **Mitigation:** .gitignore already excludes .env, .env.local, .env*.local (verified). Only .env.example is committed with placeholder values. No hardcoded connection strings in source.
- **Severity:** HIGH if violated
- **Verification:** `grep -r "neon.tech\|better-auth-secret" src/ drizzle.config.ts` returns nothing

### T-02: Connection string exposed in client bundle
- **Threat:** DATABASE_URL leaks to browser via client-side code
- **Mitigation:** db.ts is only imported in server components/actions. Next.js only exposes NEXT_PUBLIC_* env vars to client. DATABASE_URL has no NEXT_PUBLIC_ prefix.
- **Severity:** HIGH if violated
- **Verification:** db.ts has no "use client" directive; no NEXT_PUBLIC_DATABASE in codebase

### T-03: Health endpoint information disclosure
- **Threat:** Health endpoint leaks sensitive system info (versions, stack traces, DB status)
- **Mitigation:** Health endpoint returns only `{ status: "ok", ts: number }` — no DB connection test, no version info, no error details
- **Severity:** LOW
- **Verification:** route.ts returns only status and timestamp
</threat_model>

2. Replace `src/lib/db.ts` with the conditional driver implementation per D-02. Use `process.env.VERCEL` as the branch condition (Vercel sets this to "1" in all deployment contexts):

   ```typescript
   import { drizzle as drizzleNeon } from "drizzle-orm/neon-http"
   import { drizzle as drizzlePostgres } from "drizzle-orm/postgres-js"
   import { neon } from "@neondatabase/serverless"
   import postgres from "postgres"
   import * as schema from "@/db/schema"

   // process.env.VERCEL is set to "1" by Vercel in all deployment contexts
   export const db = process.env.VERCEL
     ? drizzleNeon(neon(process.env.DATABASE_URL!), { schema })
     : drizzlePostgres(postgres(process.env.DATABASE_URL!), { schema })
   ```

   Both drivers are imported statically. For a small app this is acceptable — avoids dynamic import complexity and TypeScript type issues. The ternary produces a unified `db` export that both NeonHttpDatabase and PostgresJsDatabase satisfy for all query operations used in the app.

   If TypeScript emits a type error about incompatible return types, add a type assertion:
   ```typescript

     ? drizzleNeon(neon(process.env.DATABASE_URL!), { schema })
     : drizzlePostgres(postgres(process.env.DATABASE_URL!), { schema })) as ReturnType<typeof drizzleNeon<typeof schema>>
   ```
