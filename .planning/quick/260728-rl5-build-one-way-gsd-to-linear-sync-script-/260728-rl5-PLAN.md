<decisions>
Locked by the user before planning:

- **Direction**: one-way, GSD → Linear only. Editing an issue in Linear must never write back to
  `.planning/`. Two-way sync was explicitly rejected as too much fragile glue for a solo project.
- **Structure**: Linear Project `Honey_Do` in team `HON` → project milestones `v1.0` / `v1.1` /
  `v1.2` → issues are GSD phases → sub-issues are GSD plans.
- **Trigger**: manual only this pass (`make linear-sync`). No git hooks, no Claude Code hooks, no
  CI wiring — those come later once the status mapping is proven correct against the real workspace.
- **Auth**: `LINEAR_API_KEY` read from the environment, loaded from the gitignored `.env.local` by
  the Makefile target. The Linear MCP connection authenticates the assistant interactively and is
  deliberately NOT the credential path for the script.

Status mapping (GSD signal → Linear workflow state), in precedence order:

| # | Condition | Linear state |
|---|-----------|--------------|
| 1 | Phase checked `- [x]` in ROADMAP.md | Done |
| 2 | No phase directory under `.planning/phases/` | Backlog |
| 3 | Active-execution signal: `.continue-here*.md` in the phase dir, `HANDOFF.json` naming the phase, or STATE.md reporting this phase as executing | In Progress |
| 4 | Plans exist and every `*-PLAN.md` has a matching `*-SUMMARY.md` | In Review |
| 5 | Plans exist and only some have summaries | In Progress |
| 6 | Plans exist and none have summaries | Todo |
| 7 | Phase dir has CONTEXT.md or SPEC.md but no plans | Todo |
| 8 | Phase dir exists but is empty | Backlog |

Rules 4-6 are a deliberate refinement of the original sketch: a plan set that is partially
summarized means execution is genuinely underway, and a plan set with no summaries and no active
signal is "planned, not started" — which belongs in Todo, not In Progress.
</decisions>

<task type="auto">
  <name>Task 1: Write scripts/linear-sync.mjs</name>
  <files>scripts/linear-sync.mjs</files>
  <action>
Create an ESM script matching the house style of `scripts/reset-local-password.mjs` (no
semicolons, double quotes, top-level await, Node 22 native `fetch` — no new dependencies).

Structure it in four layers:

**1. Linear API client.** POST to `https://api.linear.app/graphql`. Send personal API keys
(`lin_api_*`) in the `Authorization` header raw; send anything else as `Bearer <token>`. Throw on
HTTP failure and on a non-empty GraphQL `errors` array, surfacing the first message.

**2. `.planning/` readers.**
- Parse ROADMAP.md milestone headers (`### v1.2 (Productionization)`) and the phase checklist
  lines beneath them (`- [ ] **Phase 11: CI on Pull Requests** - goal text`) to get phase number,
  title, one-line goal, done-flag, and owning milestone.
- Parse the `### Phase N: Name` detail sections for `**Goal**`, `**Depends on**`, `**Requirements**`,
  `**Success Criteria**`, and the `Plans:` checklist, to build the issue description body.
- Resolve each phase to a directory via glob `.planning/phases/{NN}-*` and inspect it for
  `*-CONTEXT.md`, `*-SPEC.md`, `*-PLAN.md`, `*-SUMMARY.md`, and `.continue-here*.md`.
- Parse STATE.md frontmatter (`milestone`, `status`) and the `Phase: N of M` body line to detect
  the actively-executing phase.

**3. Reconciler.** Resolve, in order, creating what is missing:
- team by key `HON`
- workflow states for that team, matched by name first (Backlog / Todo / In Progress / In Review /
  Done) and falling back to Linear's state `type` (`backlog` / `unstarted` / `started` /
  `completed`) so a customized workflow still resolves
- project `Honey_Do` in that team
- project milestones `v1.0` / `v1.1` / `v1.2`
- one issue per phase, titled `Phase N: Title`
- one sub-issue per plan, titled `NN-MM: description`

Match existing issues by `.planning/linear-map.json` first, then fall back to matching the title
convention against issues already in the project. The fallback is what makes a lost map file
harmless instead of duplicate-producing.

**4. CLI.** Support `--dry-run` (print the reconciliation plan, mutate nothing) and `--check`
(verify connectivity, print resolved team/state/project IDs, exit). Exit non-zero with an
actionable message when `LINEAR_API_KEY` is missing. Print a per-phase summary line showing the
state transition applied.

Write the resolved IDs back to `.planning/linear-map.json` after a successful real run.
  </action>

  <done>Script exists, parses cleanly, and its dry-run output over the real .planning/ tree lists all 17 phases with correct derived states</done>
</task>
